# Recorder firmware v2: USB drive, one file per flight

**Status: real-flight recording verified 2026-10-22; download remains a pre-release.** The published v2 build recorded in the V7 case using live Betaflight arm/disarm and the flight controller's clock. The two retained recordings are 110.18 s and 2.82 s, both closed on `DISARM`, with intact starts and zero missing encoded frames. See the [flight-test report](../../docs/flight-test-2026-10-22.md).

**Known issue:** USB sometimes fails to appear on a cold connection until the recorder is reset. A local USB startup candidate was installed after the flight; it is not included in this published v2 source or binary, and has not been flight-tested. Repeated USB startup validation remains incomplete.

Firmware v2 drops the microSD card. The recorder stores audio in the XIAO ESP32S3's own 8 MB flash, and when you plug it into a computer it shows up as a USB drive, like a memory card.

## What you see on the computer

- A **read-only USB drive named `FPVAUDIO`**. It holds:
  - **one WAV file per flight** (arm to disarm), 16 kHz mono 16-bit;
  - `FLIGHTS.CSV`, listing every file with its start time;
  - `README.TXT`, with the steps below in plain language.
- **File names:** `FPV_<local date and time>_P<power-up>_F<flight>.WAV`, for example `FPV_20261018173825_P0005_F01.WAV` is 18 Oct 2026, 17:38:25, power-up 5, first flight. Without a clock the name is `FPV_P0005_F01_NOCLOCK.WAV`.
- **Timestamps** come from Betaflight's real-time clock over MSP (read-only), which GPS or the Betaflight configurator sets. Each WAV also carries a Broadcast WAV `bext` time reference, so DaVinci Resolve and Premiere can place it by time of day.
- **About 30 minutes** fit. After that the **oldest audio is overwritten** automatically, like a dashcam, so copy flights you want to keep.
- The drive is read-only, so you can't delete single files. It disappears while the recorder is recording and comes back with the new file a few seconds after it stops. On a Mac you may see a "Disk Not Ejected Properly" notice when a recording starts while plugged in; that's expected.
- The USB serial port stays available alongside the drive for the host tools below.
- The LED is on while recording.

## Erasing everything (format)

1. Unplug the recorder from the drone and plug it into USB power or a computer. Don't hold any button while plugging in.
2. Wait 5 seconds.
3. Press and hold the button marked **B** (BOOT, the left of the two buttons next to the USB port when the board is viewed from the top with the port facing away) for about **10 seconds**. Steady the USB plug with a finger so it doesn't wiggle; a wiggle can restart the board.
   - After 1 second the LED blinks slowly. No blinking means the wrong button: let go. The other button, R, restarts the recorder.
   - After 5 seconds it blinks fast.
   - At 10 seconds it gives **three long flashes**: everything is erased. Let go.
4. Letting go before the three flashes cancels, and nothing is erased.

Holding B through a restart puts the chip into download mode; just unplug and plug back in.

## README.TXT on the drive

The drive's `README.TXT` is generated by the firmware and covers, in plain steps:

- **Getting your audio:** plug in with a USB-C cable, copy the WAVs off the `FPVAUDIO` drive; read-only; disappears while recording.
- **One file per flight:** recording follows arm and disarm; the file name format and `FLIGHTS.CSV`.
- **When it's full:** about 30 minutes, then the oldest audio is overwritten.
- **Erasing everything:** the B-button steps above, ending with three long flashes.
- **Matching with video:** the Broadcast WAV time of day, and `audio_video_sync.py`.

## Installing

The image is for the **Seeed Studio XIAO ESP32S3 Sense (8 MB flash, OPI PSRAM)**, camera removed, wired to a spare flight-controller UART (D6/TX to FC RX, D7/RX to FC TX, GND, 115200 baud, Betaflight MSP enabled on that UART). See the [build guide](../../docs/build.md).

`bin/fpv-audio-recorder-fw-v2.bin` is a merged image of the bootloader, partition table and app, written at offset 0. It ends at 0xA0720, before the recording partition (0xB0000), so flashing it doesn't erase stored audio:

```sh
esptool --chip esp32s3 write-flash 0x0 fpv-audio-recorder-fw-v2.bin
```

The first time you move from the SD firmware (v0.1.0) or another sketch, the USB mode changes, so you may need to hold **B** while plugging in to enter download mode. Unplug and replug afterwards. The separate parts are in `bin/` too (offsets: bootloader 0x0, partitions 0x8000, boot_app0 0xE000, app 0x10000; flash mode DIO, 80 MHz, 8 MB). Checksums are in [SHA256SUMS.json](SHA256SUMS.json).

## Building from source

Arduino ESP32 core 3.3.12 and the `esp32_opus` library 1.0.3:

```sh
arduino-cli lib install esp32_opus@1.0.3
arduino-cli compile \
  --fqbn esp32:esp32:XIAO_ESP32S3:PSRAM=opi,FlashSize=8M,USBMode=default,CDCOnBoot=cdc,UploadMode=cdc \
  --build-path /tmp/fpv-recorder-build flight_recorder_flash
```

`USBMode=default` selects TinyUSB, which the drive needs; the firmware stops the build with `#error` otherwise. Use a build path without commas (the linker's map-file argument breaks on them). The app is about 590 KB of its 640 KB slot. The custom `partitions.csv` gives a 640 KB app and a 7.31 MB raw `rec` partition.

## How it records

- Opus, 16 kHz mono, 20 ms frames, 32 kbps constrained VBR, with a DC blocker and −12 dB gain. About 30.5 minutes fit.
- Audio is written in chunks of at most 0.5 s, each with a sequence number and CRC32, so a battery pull loses at most the last 0.5 s and earlier recordings stay intact.
- Arm state is read from Betaflight with MSP (read-only). Recording starts after 2 armed replies, stops after 2 disarmed replies, and stops after 3 s with no reply. The recorder never sends flight commands.
- WAVs on the drive are decoded from Opus while the computer reads them (seeking works). Copying runs at about 9–10× real time.

## Host tools (Mac, Python 3)

In [`host-tools/`](host-tools/):

- **`fetch_flash_recordings.py`** (needs `pyserial` and `ffmpeg`): finds the recorder by its USB name ("FPV Audio Recorder") without sending anything to other ports, and downloads recordings over the serial port as Ogg Opus plus WAV. Also `--list`, `--status`, `--wipe`, and `--set-clock` to give the recorder the computer's time and zone for bench tests.
- **`audio_video_sync.py`** (needs `numpy`, `scipy` and `ffmpeg`): pairs recorder WAVs with DJI O4 Pro clips by time, then estimates their offset by matching prop noise in the audio against vibration in the O4's gyro data. Check the match report and playback; the tool's timing resolution is not a guarantee of sync accuracy. It writes a clip-length WAV per matched clip and `sync-report.csv` to `~/Movies/<date> FPV audio sync/` (or `--out`); `--mux` also writes MP4 copies with the audio added. It never writes next to the source clips. It needs the `gyro2bb` tool from [telemetry-parser](https://github.com/AdrianEddy/telemetry-parser), built and placed at `host-tools/tools/gyro2bb`.

  ```sh
  python3 audio_video_sync.py /Volumes/FPVAUDIO "/path/to/DJI clips"
  ```

## Host test

[`host_test/`](host_test/) builds the firmware on a Mac against stubbed hardware (flash in memory, real Opus), records a PCM file through it, writes the virtual drive as a disk image, and checks 300 random reads against a sequential read. Build and run commands are at the top of `harness.cpp` (Homebrew `opus` and `zlib`). Optional modes: `wrap` (32-minute overwrite) and `wipe` (button format). With AddressSanitizer on, a report can occasionally appear at process exit from the stub's detached background thread; that is a test-harness teardown race, not device code.

## Verified on the bench (2026-10-18)

- The drive mounts in macOS as `FPVAUDIO` (read-only). Recordings made with the earlier flash firmware survived the update.
- Drive audio matches the serial download (correlation 0.9999). Copy speed 270–330 KB/s.
- A bench-clock recording got the right timestamped name and matching times in `FLIGHTS.CSV` and the `bext` chunk; 0 lost frames, about 41% CPU, chip 39.7 °C on USB power without airflow.
- Without a clock the next file was named `_NOCLOCK`, as expected.
- The B-button format worked on the board (the drive came back empty, no restart).
- The published binary was built from the same source as the firmware on the bench board.

## Real-flight result (2026-10-22)

- Two retained WAVs match their `FLIGHTS.CSV` durations: 110.18 s and 2.82 s, 16 kHz mono signed 16-bit PCM.
- Both entries report `DISARM`, `FC` clock and `start_overwritten=no`. Raw Opus retrieval reports zero missing encoded frames in both streams.
- The main recording’s decoded peak is −7.64 dBFS. This does not rule out microphone overload before digital attenuation; see the [audio analysis limits](../../docs/flight-test-2026-10-22.md#what-the-audio-establishes).
- This flight predates the local USB startup candidate. The published v2 source, images and flash offsets are unchanged.

## Remaining validation and integration

- Repeated USB cold starts and reconnects, late USB insertion while externally powered, and flight-controller-triggered recording under the local candidate. Testing remains incomplete after a harness wire needed resoldering.
- Power loss during flight, temperature in flight, repeated-flight reliability and wind-noise protection.
- Easy Eject: its experimental recorder mode looks for the old USB ID and doesn't find v2 yet, so [`../latest.json`](../latest.json) still points at the v0.1.0 bench image.
